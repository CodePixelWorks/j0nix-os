# Nix Shell Quote Escaping for Hyprland Lua Dispatch in System Scripts

## Symptom

A system script generated by Nix (e.g. `hyprland-post-resume-recover`) fails at
runtime with:

```
/run/current-system/sw/bin/hyprland-post-resume-recover: line 22: syntax error near unexpected token `('
```

The script appears correct in the Nix source file but the generated derivation
drops or mis-escapes quotes.

## Root cause

Nix `writeShellScript` / `writeShellScriptBin` / `pkgs.writeScript` wraps the
script body. When the body contains nested quoting (single quotes inside a
`bash -lc '...'` block, or parentheses inside single-quoted strings), the
generated script has unbalanced quotes that bash cannot parse.

### Concrete example from session 2026-06-12

Source in `nix/system/wm/hyprland.nix` (line ~194, before fix):

```nix
hyprlandPostResumeRecover = pkgs.writeShellScriptBin "hyprland-post-resume-recover" ''
  profile_bin="${config.home-manager.users.${mainUser}.home.profileDirectory}/bin"
  bash -lc '
    ...
    hyprctl dispatch 'hl.dsp.dpms({state = "on"})' >/dev/null 2>&1 || true
    ...
  '
'';
```

Nix strips the outer `''` delimiters and emits:

```bash
bash -lc '
  ...
  hyprctl dispatch 'hl.dsp.dpms({state = "on"})' >/dev/null 2>&1 || true
  ...
'
```

Bash sees the second `'` (before `hl.dsp`) as closing the `bash -lc '` string.
Everything after it is parsed as bare shell code. The `(` in `hl.dsp.dpms(...)`
then triggers: `syntax error near unexpected token '('

## Fix

Switch the outer quote of `bash -lc` from single quotes to double quotes, and
escape the inner double quotes in the `hyprctl` argument with `\"`:

```nix
hyprlandPostResumeRecover = pkgs.writeShellScriptBin "hyprland-post-resume-recover" ''
  profile_bin="${config.home-manager.users.${mainUser}.home.profileDirectory}/bin"
  bash -lc "
    ...
    hyprctl dispatch 'hl.dsp.dpms({state = \"on\"})' >/dev/null 2>&1 || true
    ...
  "
'';
```

Generated script:

```bash
bash -lc "
  ...
  hyprctl dispatch 'hl.dsp.dpms({state = \"on\"})' >/dev/null 2>&1 || true
  ...
"
```

Bash parses `\"` as `"` inside the double-quoted `bash -lc` argument. The
resulting argument passed to `bash` is:

```bash
hyprctl dispatch 'hl.dsp.dpms({state = "on"})'
```

which is exactly the correct `hyprctl dispatch` syntax.

## General rule

| Pattern | Avoid | Prefer |
|---|---|---|
| Lua dispatch string inside `bash -lc` | `bash -lc '... hyprctl dispatch 'hl.dsp.foo({...})' ... '` | `bash -lc "... hyprctl dispatch 'hl.dsp.foo({... \"key\"})' ... "` |
| `$variable` expansion needed? | Inside single-quoted `bash -lc` (won't expand) | Inside double-quoted `bash -lc` (expands) |
| `$(...)` command substitution? | Inside single-quoted `bash -lc` (won't expand) | Inside double-quoted `bash -lc` (expands) |
| Inner quotes in Lua expression | `"` inside single-quoted outer | `\"` inside double-quoted outer |

## Verification

Always use `bash -n` on the generated store path before deploying:

```bash
bash -n /nix/store/...-hyprland-post-resume-recover/bin/hyprland-post-resume-recover
```

If this returns exit code 0, the script parses correctly. If it reports a
syntax error, the quote nesting is still wrong — review the escaping before
committing.

Also verify with `nix flake check --no-build` after changes that generate
scripts — Nix will catch evaluation errors even if `bash -n` misses them.

## Other contexts where this bites

- `systemd.services.<name>.script` — uses `writeScript` internally, same quote rules apply.
- `systemd.user.services.<name>.script` — same.
- Any Nix string literal (`''` or `"`) that embeds a `bash -lc`, `bash -c`, `sh -c`, or `eval` call with nested quotes.
- Home Manager `home.file.<path>.text` when the text is a shell script containing `hyprctl dispatch`.

## The `$variable` inside single quotes trap

A related but distinct issue: when the script body needs `$profile_bin` or
`$(hyprctl ...)` expansion, single-quoted `bash -lc '...'` suppresses ALL
shell expansion. If you need variable expansion inside the `bash -lc` sub-shell,
you must use double quotes and escape accordingly.

```nix
# WRONG — $profile_bin stays literal "$profile_bin" inside single-quoted bash -lc
bash -lc '
  $profile_bin/hyprctl dispatch ...
'

# CORRECT — variable expands, inner quotes escaped
bash -lc "
  $profile_bin/hyprctl dispatch 'hl.dsp.dpms({state = \"on\"})'
"
```
